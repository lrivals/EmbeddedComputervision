- **float → fake-quant**: max |float − fake-quant| over the images, in LSB of the layer scale s_y, on the values the int8 grid can represent (the clipped ones, calibration at p99.99, are counted apart in the per-layer tables). The error accumulates through the layers; the statistical gap is the one that counts for the task.
- **fake-quant → integer**, two measures. *Per layer*: the fake-quant conv fed with the same integer input as the integer model; the gap comes only from the requantization (M0/2ⁿ against a float scale) and the rounded leaky, so it stays at 1 LSB on rare values. *End to end*: both models run from the image; the one-LSB gaps propagate and grow through the layers. This is the stage where the equivalence is only *bounded proximity*; the bound is measured, not proved.
- **integer → golden → C-sim**: every byte of every layer output equal, plus the C-sim kernel ABFT check silent. `tb_net` compares the maps that the kernel writes to DDR; "not in DDR" marks a pre-pool map of a fused maxpool or a route consumed in place, covered by the next layer that is in DDR. The rebuilt fake-quant model gives the same integers as the export on every image (20 / 20, 20 / 20, 20 / 20).

## T28.1: exhaustive and boundary tests of the operators

### Output stage (requantization, leaky, saturation)

The output stage is the only non-linear integer code between two convs: requantization,
leaky and saturation. Max-pool, route and upsample are exact copies or compares.

**Method**: for each conv of each export and each channel, the accumulator range that can
actually be reached is computed **exactly** (`bounds.acc_range`). The extrema of a linear
function over the box of int8 inputs lie at a vertex, which is reached. Over that range:

- **every** value when the range holds ≤ 2¹⁶ values;
- otherwise:
  - every value next to a step of the requantized integer that can still change the int8
    output: k·2ⁿ − 2ⁿ⁻¹ divided by M0, ±1, from the leaky saturation to qmax + 1;
  - both ends, zero;
  - 1,024 evenly spaced values.

  The output is a non-decreasing step function of the accumulator, so these points
  hold both sides of every step. `test_sweep_covers_every_step` checks this property on a
  dense range.

The same accumulators go through three implementations, which are compared byte for byte:

- the Python `conv_out`;
- the golden (`build/golden/golden_ops requant`);
- the HLS output stage `store_tile` with its RQ parallel lanes and DDR writes
  (`build/hls/tb_ops --ops`).

| Network | Channels | Accumulators compared | Python == golden == HLS |
|---|---|---|---|
| tiny-yolov2-voc | 3,181 | 16,021,501 | yes |
| tiny-yolov3-coco | 3,694 | 17,377,783 | yes |
| tiny-yolov4-coco | 3,614 | 16,917,261 | yes |
| tiny-yolov7-coco | 8,669 (512 swept exhaustively) | 55,298,264 | yes |

**Run time** (`pytest tests/test_exhaustive_ops.py`): 33 s for 105.6 M values. Python takes
5 to 12 s per network, the golden 0.1 to 0.2 s, the HLS C-sim 0.4 to 2.9 s.

**Other checks**:

- **`tb_ops` self-check** (ctest): 21.6 M accumulators. They cover random (M0, n), the int32
  extremes and the rounding boundaries, for qmax 127 and 7.
- **`test_ops_exhaustive.cpp`**: the golden against a specification in 128-bit integers
  (floor division, not shifts). It covers every n ∈ [1, 31], 200 M0 per n, every rounding
  boundary of k ∈ [−1400, 1400] ± 1 and the int32 extremes: 31 M assertions.
- **SiLU** (T26.2): the integer SiLU is a requantization to the table scale, then a 256-entry
  table. Python == golden == HLS on every accumulator around each of the 256 table inputs,
  for 5 random (s_mid, s_out, M0, n, qmax).

### Finding: the golden leaky overflowed int32

The first run of `test_ops_exhaustive.cpp` failed. `golden::leaky_int` computed 13·y in
int32, which overflows (undefined behaviour) for y < −165,191,049. The Python computes it in
int64.

- **Effect on the exports**: none. The reachable requantized values stay above −24,000 on
  the four exports, and the M0·2⁻ⁿ multipliers stay ≤ 0.023.
- **Effect on the argument**: it was a hole in the contract "Python == golden for every
  int32".
- **Fix**: the product is now on 64 bits (`conv.hpp`). The HLS reuses the function: 13·y on
  36 bits, a constant multiply.
- **Check**: every bit-exact test is unchanged (`make csim-gcc`, `make golden-check`, 103
  layers in `tb_conv`, 158 layer outputs in `tb_net`).

The same review made a second precondition explicit: the requantization equals the Python
only when **M0 < 2ⁿ** (multiplier < 1). Otherwise the shifted value can leave int32, which the
C++ truncates and the Python does not. `golden::Model::load` now rejects an export that breaks
it. All 103 layers meet it.

### Tables (LUT)

For each head of each export, the σ, e^t and softmax e^{d·s} tables loaded by the golden
from `luts.bin`, indexed as `hw_postproc` indexes them, are compared over their 256 inputs.
They equal the tables recomputed in Python from the head scale (`test_luts_python_golden`).

## T28.2: SMT proof of the scalar kernels

`python tools/prove_kernels.py` (z3 5.3.1, optional extra `formal`) states the following
obligations:

- **Model**: the C++ of `requantize`, `leaky_int` and `clip_q`, re-expressed in z3
  bit-vectors with the C++ widths.
- **Specification**: the Python, written as mathematics. Floor division is stated by its
  defining inequalities, over 72-bit exact integers.
- **Quantifiers**: for **all** int32 accumulators, all M0 with 0 < M0 < 2ⁿ, all
  qmax ∈ [1, 127], and every shift n ∈ [1, 31] (one query per n).

| Obligation | Queries | Result | Solver time |
|---|---|---|---|
| (a) `int64(acc)·M0 + 2ⁿ⁻¹` does not overflow int64 | 31 | proved | ≈ 5 s |
| (b) the shifted value fits int32 (the cast loses nothing) | 31 | proved | ≈ 52 s |
| (c) y = ⌊(acc·M0 + 2ⁿ⁻¹)/2ⁿ⌋ | 31 | proved | ≈ 50 s |
| (d) leaky = y if y > 0, else ⌊(13y + 64)/128⌋, ∀ y int32 | 1 | proved | < 0.1 s |
| (e) clip to [−qmax, qmax], fits int8 | 1 | proved | < 0.1 s |

The run proves 95 / 95 obligations in 135 s, including the loading of the four exports. The
longest query takes ≈ 12 s (n = 31).

**Mutants** (`--mutant`), which must be caught:

| Mutant | Counter-example printed |
|---|---|
| no rounding term (`>> n` of the bare product) | n = 20: acc = −985,670,293, M0 = 1,031,404 |
| leaky with 13·y on 32 bits (the code before T28.1) | y = −1,636,502,221 |

### No int32 overflow of the accumulator, per layer

This is proved from the exported int8 weights.

- **Extrema**: the extrema of Σ w·x + b over x ∈ [−128, 127]ⁿ are those of
  `bounds.acc_range`. A z3 query checks this vertex lemma on a random layer.
- **Partial sums**: every partial sum of the tiled loop (a subset of the products, without
  the bias, which `store_tile` adds last) lies between the sum of the negative and the sum
  of the positive per-product extrema. The HLS `acc_t` register is therefore covered too.

| Network | Convs | Widest accumulator (bits, sign incl.) | int32 overflow | M0 < 2ⁿ |
|---|---|---|---|---|
| tiny-yolov2-voc | 9 | 27 (L13, ±52,931,184) | none | all |
| tiny-yolov3-coco | 13 | 25 (L12, ±16,527,467) | none | all |
| tiny-yolov4-coco | 21 | 25 (L26, ±16,168,086) | none | all |
| tiny-yolov7-coco | 60 | 25 (L30, ±9,234,011) | none | all |

The T4.3 prose bound of L13 was Σ|q_w|·127 + |q_b| = 2^25.7. The exact bound with inputs
down to −128 is 2^25.66: 26 bits plus the sign.

### Residual risk

- **Hand-written model**: the z3 model is written by hand from the C++ source. A gap between
  the two is covered by T28.1, which runs the real code.
- **Toolchain**: the proof says nothing of what Vitis HLS does to the C++ (T28.4, co-sim,
  board).
- **Scope**: the composition of the scalar kernels into the tiled conv is covered by the
  bit-exact tests on the dumps (golden == C-sim == Python on every layer), not by the
  proof.

## T28.4: tool-chain risks

Vitis HLS and Vivado sit between the C++ that is checked (C-sim == golden == Python, T28.0)
and the bitstream. Each transformation that could break the equivalence, with what the kernel
actually uses and the check that covers it:

| Transformation | In the kernels | Risk | Covered by |
|---|---|---|---|
| `PIPELINE II=1` (13) and `DEPENDENCE variable=out_buf inter false` (`conv_pe.cpp`) | MAC loop | the pragma *asserts* there is no loop-carried dependence on `out_buf`; if it is false, the RTL reads a stale accumulator while C-sim stays right | co-sim (RTL schedule run on the dumps), board hash (T28.5). C-sim cannot see it. |
| `UNROLL` (10), `ARRAY_PARTITION` (18) | Tm × Tn PE array, tile buffers | none on the values (scheduling only), unless a partition creates a port conflict that HLS resolves by changing II | synthesis report (II), co-sim |
| `DATAFLOW` + `STREAM` (11) | stream kernel (`hls/stream`) | FIFO depth too small → deadlock; a read before write the C-sim order hides | co-sim (`make hls-cosim-stream`), which detects deadlocks |
| `ap_int` widths and overflow | `ap_int<8>`, `<32>` (acc), packed MAC `<27>`·`<18>` → `<45>` → `<48>` | default modes are `AP_TRN` / `AP_WRAP`: a narrowing assignment wraps silently. No `ap_fixed` and no `AP_RND` / `AP_SAT` in the kernels. | C-sim with the open-source `ap_int` headers (same semantics as Vitis), T28.2 (no int32 overflow of the accumulator, proved per layer), `tb_pack` (all int8 triplets of the packed MAC). The packed PE runs in native integers in `csim-gcc` (`ACC_NO_APINT`, 7× faster); its `ap_int` product is checked by `tb_pack`. |
| `BIND_OP op=mul impl=dsp` and DSP inference | packed product (T23) | the DSP48E2 pre-adder / P register width: a product wider than 48 bits would wrap | `tb_pack` (exhaustive), PACK_N bound by `static_assert`, co-sim |
| Retiming, register duplication, `phys_opt` (Vivado) | whole design | functionally neutral by construction, unless timing is not met | timing report (WNS ≥ 0), board hash. A design that fails timing is not loaded. |
| BRAM / ROM initialization | weights in ROM in the stream kernel (`STREAM_ROM`, `gen_stream_rom.py`) | a ROM initialized from another export than the one tested | the C-sim of the stream kernel built with `STREAM_ROM` (`tb_stream_rom`), the bitstream and model hashes recorded with the board row (T28.5) |
| `INTERFACE m_axi` (32), word width, `-m_axi_addr64` | DDR ports | burst, alignment or byte-order mismatch with the driver | `driver::run` in C-sim uses the same arena layout; co-sim runs the real AXI adapters; `check-regmap` (register offsets) |

**Tool qualification.** DO-178C §12.2 (with DO-330) asks to qualify a tool whose output is
not verified when it can insert an error. A synthesis tool is a TQL-1 to TQL-3 tool (criterion
1, it builds the airborne item), and qualifying Vitis HLS is out of reach. Here its output is
verified instead:
- the RTL is run against the golden in co-sim;
- the bitstream is run against it on the board, with every layer hashed (T28.5).

This is the route DO-254 also gives for complex hardware ("output verified by an
independent means"). So the tool does not need to be qualified, as long as these
checks run on the configuration that is shipped.

What these checks do not cover:
- configuration-memory upsets in the field (M25, SEM IP);
- timing outside the tested corner;
- inputs outside the test images, for layers whose co-sim covers only one image
  (`cosim.tcl` runs one image per network).

## T28.6: post-processing equivalence and properties

`python tools/equivalence.py postproc` (4 s), `python/tests/test_postproc_props.py`, and
`tb_post` in `make csim-gcc`. Networks: Tiny-YOLOv2 and Tiny-YOLOv3. `yolo_post` does not
support `scale_x_y` / `new_coords`, so v4 and v7 are out of scope.

**Equivalence.**
- The Python reference (`hw_postproc.run`) equals the golden `hwpp` on the 20 images of
  T28.0 per network, at thresholds 0.005 and 0.25 (40 / 40 each).
- The HLS kernel `yolo_post` equals the golden on the same images
  (`tb_post --model build/equivalence/model`, 43 / 43 cases each), and on the 3 dumps plus
  1,000 random heads in `make csim-gcc`. The overflow counter is included.
- On the full VOC2007 test set, the end-to-end effect is measured in
  [postproc_hw.md](postproc_hw.md): −0.10 mAP against the sorted NMS on the host.

**Properties** (checked on every candidate stream of these images, and on 50 random streams):

| Property | Result |
|---|---|
| No candidate dropped below capacity: for cap ∈ {1, 2, 4, …, 256}, overflow = 0 ⟺ the slots used with unlimited slots ≤ cap, and then the result equals the unlimited one | **holds** (Python, every cap). The kernel equals Python, overflow included. At most 79 (v2) and 134 (v3) of the 256 slots are used on these images. |
| Overflow flagged, never silent | **holds**: the counter is the number of candidates lost. In `tb_post`, the all-classes case (more candidates than slots, boxes apart) must report overflow > 0. |
| Result independent of the order of the cells | **does not hold for the raw stream**. A random permutation of the candidate stream changes the kept boxes in 363 / 400 (v2) and 294 / 400 (v3) cases. On 18 / 20 (v2) and 12 / 20 (v3) images the result differs from the classic NMS. This is the no-sort NMS of 2024-zhang by design, see the chain a < b < c in `test_hw_postproc.py`. |
| …for the stream sorted by (score ↓, box) | **holds**: equal to the classic NMS (§8.2) whatever the order of the cells. |

The kernel order is fixed (head, anchor, row, column, class), so its output is
deterministic and equal to the golden. It is not invariant to the order of the cells, which
is what the acceptance asked. Making it invariant needs a sort, or at least a total order
on the candidates, before the NMS: a sorting network or a heap over the survivors, at the
cost of the 0.38 ms budget of 2024-zhang. The measured cost of not doing it is −0.10 mAP.
This is a design decision to record in the assurance case (M31), not a defect of the
implementation.
